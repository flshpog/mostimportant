**can a vite + react app live at `/board`?** yes, and nothing existing has to change:

- build with `base: '/board/'` and commit the output into `fiovivor.org/board/`
- add a `.nojekyll` at the site root, or jekyll may drop files starting with `_`
- pages has no SPA fallback, so use **hash routing** (`/board/#/tribe/x`) instead of editing `404.html`
- add the hub link in `build_index.py`, not by hand in `index.html`, because rerunning the script overwrites it

## 2. proposed repo structure

turn `mostimportant` into an npm-workspaces monorepo, **without moving the existing bot**:

```
mostimportant/
  package.json            # add "workspaces": ["packages/*", "apps/*"]
  src/                    # existing bot, unchanged layout
    board/                # NEW: game server module (persistence, http, ws, oauth)
    commands/board/       # NEW: /roll, host board commands
  config/
    season3-board.json    # NEW: season-config (all numeric rules)
  packages/
    types/                # shared TS types: Space, events, state, API payloads
    board-data/           # board.json + zod schema + validator script
    engine/               # pure TS engine, no IO, vitest tests
  apps/
    web/                  # vite + react + react-three-fiber + drei
  scripts/
    deploy-web.js         # builds apps/web and copies dist into ../fiovivor.org/board
```

why this shape:

- **typescript only where the spec needs it.** the new packages are TS and compile to
  commonjs, so the existing JS bot can `require('@everest/engine')` with no rewrite.
- **the game server lives inside the bot process** (`src/board/`). there is one host, one
  copy of state, and discord and the website see the same events immediately. that
  avoids running a second process and syncing state between the two.
- **shared types in one repo.** the web source sits next to the engine, so `types` is
  a workspace import, not a copy. only the built static files go to `fiovivor.org`.
- **http + websocket:** node's built-in `http` plus the `ws` package. no express. this
  respects the CLAUDE.md "don't introduce a new framework" rule; the API surface is small.
- **tests:** `vitest` for `engine` and `board-data`. the existing bot stays untested
  unless you want that too.
- **2D discord image:** `@napi-rs/canvas` (prebuilt binaries, so no native build on
  windows). jimp can't draw shapes or text well enough for a board.

## 3. persistence

CLAUDE.md says to match the existing storage and not to add a database, so the
proposal is JSON files designed for an event log:

- `data/board/<tribe>.events.jsonl`: **append-only** event log, one event per line.
  this is the source of truth: season history, audit trail and undo all come from it.
- `data/board/<tribe>.state.json`: snapshot of current state, written with
  temp-file + rename so a crash mid-write can't corrupt it. it can always be rebuilt
  by replaying the log.
- **undo** = drop the last event (or event group) and replay. the engine is
  deterministic given recorded dice, so replay is exact.
- four tribes × a slow pace = a few thousand events a season. JSON is plenty.

sqlite would also work (if the host has a persistent disk), but it breaks the
existing CLAUDE.md rule. it's only worth it if you'd rather have it (question 14).

## 4. hosting, domain, WSS, CORS

the static site can't run the server, so the bot process needs a **public HTTPS +
WSS endpoint**. proposed hostname: `board.fiovivor.org`.

how depends on where the bot runs (question 12):

- **option A, VPS / cloud box with a public IP:** run caddy as a reverse proxy
  (`board.fiovivor.org` → `localhost:<port>`). caddy gets and renews TLS
  automatically. point a DNS A record at the box.
- **option B, home PC or any host without open ports:** use a **cloudflare tunnel**
  (`cloudflared`). there's no port forwarding, and TLS and DNS are handled by
  cloudflare. you already use cloudflare R2, so the account exists. this needs the
  `fiovivor.org` DNS to be on cloudflare (question 20).
- **option C, managed host (railway/render/etc):** they provide HTTPS. you'd still
  need a persistent disk for `data/`.

either way:

- **CORS and the websocket origin check** allow `https://fiovivor.org` (plus
  `http://localhost:5173` in dev). the origin list goes in config.
- **discord oauth2:** the site sends you to discord, discord redirects to
  `https://board.fiovivor.org/auth/callback`, and the server checks guild membership
  and tribe role, then hands the site a signed session token. this needs the bot
  application's **client secret** in `.env` (never committed) and the redirect URI
  added in the discord developer portal.
- **the port, origins and public URL** live in config/`.env`, not code.
